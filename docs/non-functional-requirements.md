# SaaS非機能要件定義書

## 1. 文書情報

| 項目 | 内容 |
|---|---|
| 対象 | 日本国内向け一般業務SaaS |
| データ特性 | 個人情報および顧客機密情報を含む |
| 想定方式 | パブリッククラウド上のマルチテナントサービス |
| 基準時刻 | 日本標準時（JST） |
| ステータス | 初期基準 |

本書の数値はサービス開始時の基準値である。契約、リスク評価、負荷試験の結果により変更する場合は、変更理由、承認者、適用日を記録する。

## 2. サービスレベル

### 2.1 可用性

| ID | 要件 | 測定・受入基準 |
|---|---|---|
| AVL-01 | 月間稼働率を99.9%以上とする | 外形監視により1分間隔で測定する |
| AVL-02 | 計画停止は原則として5営業日前までに通知する | 通知履歴を保存する |
| AVL-03 | 単一障害点を排除する | 本番構成レビューと障害試験で確認する |
| AVL-04 | 重大障害を24時間365日検知できるようにする | 監視通知の定期試験を実施する |

月間稼働率は次式で算出する。

```text
月間稼働率 = (総時間 - 対象停止時間) / 総時間 * 100
```

事前通知済みの計画停止、利用者環境に起因する障害、不可抗力をSLA計算から除外する場合は、契約または利用規約に明記する。

### 2.2 障害復旧・事業継続

| ID | 要件 | 測定・受入基準 |
|---|---|---|
| BCP-01 | 重大障害からのRTOを4時間以内とする | 年1回以上の復旧訓練で確認する |
| BCP-02 | 永続データのRPOを1時間以内とする | バックアップ設定と復元試験で確認する |
| BCP-03 | 障害対応手順、連絡網、復旧判断者を文書化する | 半年ごとに内容をレビューする |
| BCP-04 | 復旧後にデータ整合性を検証する | 件数、参照整合性、主要業務データを確認する |

### 2.3 性能・拡張性

| ID | 要件 | 測定・受入基準 |
|---|---|---|
| PRF-01 | 通常操作の応答時間をp95で2秒以内とする | 本番相当データを用いた負荷試験で測定する |
| PRF-02 | 検索・集計処理の応答時間をp95で5秒以内とする | 非同期処理として設計した機能は対象外とする |
| PRF-03 | 通常想定負荷の2倍までサービスを継続できること | エラー率1%未満を負荷試験で確認する |
| PRF-04 | アプリケーション層を水平スケール可能にする | セッションや一時データを特定ノードに依存させない |
| PRF-05 | バッチ処理がオンライン処理の性能目標を阻害しないこと | 同時実行試験で確認する |

想定同時利用者数、データ量、APIリクエスト数は、事業計画確定後に負荷試験条件として別途定義する。

## 3. セキュリティ・プライバシー

### 3.1 テナント分離・アクセス制御

| ID | 要件 | 測定・受入基準 |
|---|---|---|
| SEC-01 | データ、権限、キャッシュ、ファイル、ログをテナント単位で論理分離する | 別テナントへのアクセス拒否を自動テストする |
| SEC-02 | RBACを採用し、管理者と一般利用者の権限を分離する | 権限マトリクスと認可テストで確認する |
| SEC-03 | サーバー側で全リクエストの認証・認可を検証する | URLやIDの改変による権限迂回を試験する |
| SEC-04 | 管理者にMFAを必須とする | MFA未設定時に管理機能を利用できないことを確認する |
| SEC-05 | 連続認証失敗時の抑止とセッション有効期限を設定する | セキュリティ試験で確認する |
| SEC-06 | 運用者権限に最小権限と定期棚卸しを適用する | 四半期ごとに権限をレビューする |

### 3.2 暗号化・秘密情報

| ID | 要件 | 測定・受入基準 |
|---|---|---|
| SEC-07 | 外部通信をTLS 1.2以上で暗号化する | 構成検査で脆弱なプロトコルを拒否することを確認する |
| SEC-08 | データベース、ファイル、バックアップを保存時に暗号化する | クラウド設定と鍵設定をレビューする |
| SEC-09 | パスワードを安全な適応型ハッシュで保存する | 平文および復号可能な形式で保存されていないことを確認する |
| SEC-10 | APIキーや認証情報を秘密情報管理サービスで管理する | ソースコードとログへの混入をスキャンする |
| SEC-11 | 暗号鍵のアクセス制御、監査、ローテーション手順を整備する | 年1回以上レビューする |

### 3.3 脆弱性・監査

| ID | 要件 | 測定・受入基準 |
|---|---|---|
| SEC-12 | コード、依存関係、コンテナを継続的にスキャンする | CIで重大な検出がある場合はリリースを停止する |
| SEC-13 | 重大脆弱性は検知から72時間以内に緩和または修正する | チケットの検知日時と対応日時で確認する |
| SEC-14 | リリース前および年1回以上、脆弱性診断を実施する | 報告書と是正記録を保存する |
| SEC-15 | ログイン、権限変更、データ更新・削除、管理操作を監査記録に残す | 操作者、日時、テナント、対象、操作、結果を記録する |
| SEC-16 | 監査ログを改ざん困難な場所に1年以上保存する | 削除権限と保存期間の設定をレビューする |
| SEC-17 | ログにパスワード、トークン、不要な個人情報を出力しない | 自動スキャンとレビューで確認する |

### 3.4 個人情報・データ管理

| ID | 要件 | 測定・受入基準 |
|---|---|---|
| DAT-01 | 個人情報の利用目的、取得項目、保存期間を明確にする | プライバシーポリシーとデータ台帳をレビューする |
| DAT-02 | 顧客データは原則として国内リージョンに保存する | 利用サービスと保存先を構成台帳で管理する |
| DAT-03 | 契約終了後30日以内に顧客データを削除する | 削除処理記録を保存する |
| DAT-04 | 法令または契約上の保存義務があるデータは、対象と期限を分離管理する | 例外の根拠、承認者、削除予定日を記録する |
| DAT-05 | データの出力、訂正、削除依頼に対応できること | 対応手順と本人確認手順を整備する |
| DAT-06 | 委託先と外部サービスのデータ取扱いを管理する | 年1回以上、委託先台帳と契約をレビューする |

## 4. 運用・保守

### 4.1 バックアップ

| ID | 要件 | 測定・受入基準 |
|---|---|---|
| OPS-01 | RPOを満たす頻度で自動バックアップを取得する | バックアップジョブの成功を毎日監視する |
| OPS-02 | バックアップを世代管理し、本番データと障害ドメインを分離する | 保存先と保持設定をレビューする |
| OPS-03 | 四半期ごとにバックアップからの復元試験を実施する | 復元時間と整合性検証結果を記録する |
| OPS-04 | バックアップにも本番データと同等の暗号化・アクセス制御を適用する | 権限と暗号化設定をレビューする |

### 4.2 監視・インシデント対応

| ID | 要件 | 測定・受入基準 |
|---|---|---|
| OPS-05 | 可用性、応答時間、エラー率、リソース、ジョブ、バックアップを監視する | 各監視項目に閾値、通知先、対応手順を設定する |
| OPS-06 | 重大障害の初報を検知または受付から1時間以内に行う | 通知履歴で確認する |
| OPS-07 | 重大障害の復旧まで定期的に状況を更新する | 更新間隔はインシデント手順に定義する |
| OPS-08 | 重大障害後に原因、影響、再発防止策を記録する | 原則5営業日以内に事後レビューを完了する |
| OPS-09 | アラートの疎通と当番連絡先を定期的に試験する | 月1回以上実施する |

### 4.3 変更・リリース管理

| ID | 要件 | 測定・受入基準 |
|---|---|---|
| MNT-01 | インフラ構成をコードで管理し、変更履歴を保持する | 本番への手動変更を例外管理する |
| MNT-02 | コードレビューと自動テストを通過した変更のみ本番反映する | CI/CDの承認履歴を保存する |
| MNT-03 | リリースごとにロールバック手順を準備する | 本番反映前に適用可否を確認する |
| MNT-04 | 緊急変更は事後レビューを実施する | 変更理由、実施者、影響を記録する |
| MNT-05 | 本番環境へのアクセスと操作を記録する | 定期的に監査ログをレビューする |

| ID | 要件 | 測定・受入基準 |

## 6. サポート・コスト

| ID | 要件 | 測定・受入基準 |
|---|---|---|
| SUP-01 | 通常サポート時間を平日9:00～18:00 JSTとする | 休業日と窓口を利用者に明示する |
| SUP-02 | 重大障害の検知および受付体制を24時間365日確保する | 連絡経路と対応責任者を定義する |
| CST-01 | クラウド利用料をサービス、環境、主要機能単位で把握する | タグまたはアカウント分離により集計する |
| CST-02 | 月次予算と段階的な超過アラートを設定する | 毎月、予算差異と増加要因をレビューする |
| CST-03 | テナントまたは契約プラン別の利用量を計測可能にする | 課金・容量計画に必要な指標を保存する |

## 7. リリース受入基準

初回本番リリースまでに、次の条件をすべて満たす。

- 性能目標と想定最大同時利用数を負荷試験で満たす。
- RTOおよびRPOを障害復旧試験で満たす。
- テナント境界と権限境界を越えられないことを自動テストで確認する。
- 脆弱性診断の重大・高リスク指摘を解消するか、期限付きのリスク受容を承認する。
- バックアップからの復元とデータ整合性を確認する。
- 監視、アラート、障害連絡、データ削除、ロールバックの手順を文書化する。
- SLAの対象、除外条件、計測方法を利用規約または契約に反映する。

## 8. 未確定事項

次の項目は事業・システム設計の確定時に数値化し、本書へ反映する。

- 最大契約テナント数、登録利用者数、最大同時利用者数
- テナント当たりのデータ容量とファイル容量
- 通常時およびピーク時のAPIリクエスト数
- バックアップの具体的な保持世代と保持期間
- サポート対象外となる端末、ブラウザ、外部連携
- 障害重要度の定義と重要度別の応答・復旧目標
- 利用するクラウド、リージョン、可用性ゾーン、災害対策方式
